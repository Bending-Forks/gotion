# Gotion — Project Instructions

## What this is

Gotion is a self-hosted Notion clone: the joint deliverable for the university courses **SAP** (Software Architecture and Platforms) and **SPE** (Software Process Engineering). Both courses share this single project, so their requirements apply simultaneously and every deliverable must satisfy both.

Current state: design phase. The repo holds the Jekyll report in `docs/`, published to GitHub Pages by the CI on every push to `main`, with one chapter per stage of the project. Introduction and Analysis are written; Design has the strategic and tactical design (the Page Block Tree follows ADR-01: the CRDT keeps the rules two concurrent operations could break, Editing checks the others on its replica before the append), the Components and Connectors views (an overview with its element catalog, then event-based, data flow and repository; the Membership subscriptions and queries follow ADR-03) and the ADRs (ADR-01, ADR-05 and ADR-08 accepted, ADR-02, ADR-03, ADR-04, ADR-06, ADR-07 and ADR-09 proposed; ADR-05 uses a Transactional Outbox with a Polling Publisher in Account, Membership and Discussion, excludes Notification because it publishes nothing, and leaves Editing on direct publication with its accepted event-loss limit; ADR-04 puts Editing on Node.js so it shares the CRDT package with the client, the other four services and the API gateway on Go; ADR-06 gives each service a PostgreSQL server of its own, the session log of Editing included, with migrations at start; ADR-07 gives each runtime a microservice chassis assembled from libraries, Watermill with its SQL outbox and Forwarder for Go, Fastify for Editing, no OpenTelemetry; ADR-08 writes the contracts in JSON Schema, with no schema registry; ADR-09 makes the sign-in token a JWT that Account signs with Ed25519, carried in an `HttpOnly`, `SameSite=Strict` cookie that lasts 8 h with no refresh token, checked by the gateway with `golang-jwt/jwt/v5` from the `token/` package of the Go chassis, which passes the identity on to the services in `X-User-Id`), the Microservices section (decomposition by subdomain, one service per bounded context; a table per service with its client API, the queries it answers and asks, the events it publishes and consumes, and its store; the synchronous dependencies and their failure policy; state and scaling, with the routing of each page to one Editing instance moved here from the C&C views; the contracts between services, with the event envelope, the `api/` folder of each service and one meaning per status code; the API Composition of the Workspace directory in the gateway), the Patterns section (a catalog of the patterns applied, including Transactional Outbox and Polling Publisher, and Microservice Chassis, Externalized Configuration and Server-side discovery as cross-cutting concerns, grouped by category and each linked to where it is described, the two deployment patterns linked to Deployment; then Observability: the health checks and the metrics that measure each runtime scenario; then Event delivery: outbox publication for the three Go publishers (ADR-05), the remaining direct-publication limit in Editing, and the cascades across contexts as a choreography that needs no saga), Hexagonal Architecture (one picture with the hexagon of each service, its ports and adapters, one under the other, `hexagonal.drawio` next to the C&C views, exported by the same `render.sh`); Implementation describes the Editing client (BlockNote), the libraries of the Go services and the API gateway (the sign-in token of ADR-09 included) and those of Editing, adapter by adapter (ADR-07), under Testing the consumer-driven contract tests (one per relation of the context map plus the gateway's queries: JSON examples written by the consumer in the `api/contracts/<consumer>/` of its provider, checked on both sides with a JSON Schema validator and a subset match, no Pact), and, under Multiplatform, the runtimes of ADR-04 and how Editing and the CRDT run their TypeScript (type stripping, `tsc` for the types only, `node:test`); DevOps describes the Project Structure (the packages of the monorepo, the inner layout of each service, the packages of the chassis), VCS & Repo and CI/CD as they stand now, and opens Deployment with the Kubernetes picture; the rest (SemVer and releases, the rest of Deployment, benchmark) is written at the end of development; Conclusions is a stub. The skeleton of the monorepo is in place, with no logic yet: a Go module per Go service and for the chassis, joined by `go.work`, and the npm workspaces of Editing and the CRDT package; the web client is not there yet. The CI builds and tests them in the `go` and `node` jobs. The first contracts are written: the event envelope in `api/envelope.schema.json` and the specifications of Account and Membership in `services/<service>/api/` (OpenAPI 3.1 with the client API under `/v1/` and the queries under `/internal/v1/`, AsyncAPI 3.0 with one channel per context, the body of each event version in `events/<event>.v<n>.json`).

## Repository conventions

The report lives in `docs/`; the root holds `README.md`, `api/` (the event envelope shared by every service), `tests/` (Node tests of the report's scripts, of `.github/scripts/`, of the envelope and of the validity of every `services/*/api/` specification, with Redocly for OpenAPI and AsyncAPI alike; `npm ci` first), `scripts/` (`ff-merge.sh`, `new-worktree.sh`, `remove-worktree.sh`), `.github/`, `.husky/`, the code (`services/`, `packages/`) and the files that join it: `go.work`, the `workspaces` globs of `package.json` (npm takes only the folders with a `package.json`), `tsconfig.base.json`. The report is a set of chapter pages, each with `title`, `icon` (an emoji, the chapter's icon in the Notion-like sidebar) and `nav_order` front matter, rendered through `docs/_layouts/chapter.html` (sidebar nav built automatically from `nav_order`, the current chapter's headings nested under it). Chapters, in order:

1. `docs/introduction.md` — Team, Scenario, Deliverables (stub)
2. `docs/analysis.md` — pulls in, in order, `docs/_includes/business-requirements.md`, `docs/_includes/subdomains.md` (the subdomains of the business, found from the requirements, with their core/supporting/generic type), `docs/_includes/functional-requirements.md` (user stories, grouped by those subdomains, plus an "Out of scope for now" table of stories kept aside without IDs, so active stories are numbered consecutively), `docs/_includes/quality-attributes.md` (Quality Attributes as QA-xx six-part scenarios: Source → Stimulus → Artifact → Environment → Response → Response measure, grouped by category — Performance, Availability, Data Consistency, Security, Deployability, Modifiability, Accessibility), `docs/_includes/event-storming.md` (the ten steps of the board, numbered, plus the open pain points; the pivotal events confirm the subdomains, and the bounded contexts of step 10 are the bridge to Design) and `docs/_includes/ubiquitous-language.md` (the glossary, one table per bounded context)
3. `docs/design.md` — an intro, then pulls in `docs/_includes/strategic-design.md` (Bounded Contexts, Context Map; the context map picture is generated from `docs/assets/context-map/gotion.cml` by `docs/assets/context-map/render.sh`, which needs the Context Mapper CLI `cm` and Graphviz `dot`), `docs/_includes/tactical-design.md` (Tactical Design: the aggregates per bounded context with Mermaid class diagrams, rules across aggregates, roles, changes from the board), `docs/_includes/architecture.md` (Components and Connectors, Hexagonal Architecture; the C&C pictures, an overview `gotion` plus one per style (`event-based`, `data-flow`, `repository`), are exported from the `.drawio` files in `docs/assets/components-and-connectors/` by `render.sh` next to them, which needs the draw.io CLI (`drawio`, or the command in `$DRAWIO`); keep `html=0` and no `whiteSpace=wrap` in their styles, or the SVGs embed a PNG per label), `docs/_includes/microservices.md` (Decomposition, Services, Dependencies at run time, API Composition, State and scaling, Contracts) and `docs/_includes/patterns.md` (catalog of the patterns, Observability, Event delivery), then `docs/_includes/adr.md` (the Architecture Decision Records, ADR-xx, in the course format: Title, Status, Context, Decision, Consequences, Compliance)
4. `docs/implementation.md` — Microservices, Testing, Multiplatform, Experiments, Monitoring (only the Editing client, the libraries of the services, the contract tests and Multiplatform so far)
5. `docs/devops.md` — Project Structure, VCS & Repo, Quality Assurance, CI/CD, Deployment, Benchmark (Project Structure, VCS & Repo and CI/CD so far, Deployment only its opening; the pictures `monorepo` and `deployment` are exported from the `.drawio` files in `docs/assets/devops/` by `render.sh` next to them)
6. `docs/conclusions.md` (stub)

Requirements now live only in `docs/_includes/functional-requirements.md` and `docs/_includes/quality-attributes.md` (plain Markdown, included from `docs/analysis.md`) — there is no separate DDD/Gherkin spec anymore, and no `ddd/` or `features/` directory. Don't recreate that structure; extend the two includes instead. When a chapter's content is written, fill its existing stub headings rather than restructuring — the chapter order and headings were already agreed with the co-author.

Code conventions:

- Go: one module per service and one for the chassis, module path `github.com/Bending-Forks/gotion/<path>`, `go 1.25.0`. From the root `./...` does not reach into the modules of the workspace: use `$(go list -m -f '{{.Dir}}/...')`, or the path of one module (`go test ./services/account/...`).
- TypeScript in Editing and the CRDT package: Node.js runs the sources with type stripping, so only erasable syntax (no `enum`, `namespace` or parameter properties) and relative imports ending in `.ts`; `tsc` only checks the types (`npm run build`), with the options of `tsconfig.base.json`; tests on `node:test`. The CRDT package is exported as source and has neither DOM nor Node types. The web client uses Vite and Vitest.
- Instructions for Claude Code: the rules every hexagon shares are in `.claude/rules/hexagon.md` (path-scoped to the five services with a hexagon), the conventions of all Go code in `.claude/rules/go.md`, the rules of one package in `<package>/.claude/rules/<package>.md`, which loads when Claude touches a file of that package. A `.claude/CLAUDE.md` or `.claude/settings.json` inside a package is read only when Claude is started from that folder, so don't use them. The procedures the project repeats are skills: `domain-event`, `fitness-function`, `test-strategy`, `observability`, `deployment` and `pr-page` in `.claude/skills/`; `aggregate` and `service-contract` in `services/.claude/skills/` and `ci-cd` in `.github/.claude/skills/`, which load the first time Claude touches a file in that folder. `golang-concurrency` and `golang-safety` in `.claude/skills/` are copies of samber/cc-skills-golang at commit `d68d80a` (MIT, the `LICENSE` is next to each), which load with the first Go file; the copies drop the `allowed-tools` line, so the permissions of the project apply. To update them, copy them again and drop that line. The root `.claude/settings.json` enables the Superpowers plugin. Install it once for your user and disable it there, `claude plugin install superpowers@claude-plugins-official && claude plugin disable superpowers@claude-plugins-official --scope user`: the project settings then turn it on in every checkout and worktree of Gotion, and nowhere else. An install with `--scope project` is bound to the path of one folder, so it stops working when the worktree moves and never reaches the others. The same settings enable the `humanizer` plugin, which `pr-page` uses, from its own marketplace: Claude Code offers to install it when you trust the folder, or install it for your user with `claude plugin marketplace add blader/humanizer && claude plugin install humanizer@humanizer`.

Markdown prose is not hard-wrapped: each paragraph, list item or table row is one line in the source, however long. Break lines only where Markdown needs it (a new paragraph, list item, heading, table row or code block), never at a fixed column; the renderer wraps the text. Older parts of the report are still wrapped at about 100 columns: when you change a paragraph there, join it into one line in the same change.

## Git workflow

- Signed commits only, titles in Conventional Commits. The `.husky/commit-msg` hook checks the title; `npm install` installs it through husky. CI checks every commit of a PR again, so `--no-verify` doesn't skip it. The `.husky/pre-push` hook refuses to delete a remote branch that an open PR comes from or goes into, since GitHub would close the PR.
- `main` is the only long-lived branch, for both the code and the report. Work on a feature branch and open a PR against `main`; `main` takes no other pushes.
- Work on a branch of your own. To keep several tasks apart at once, give each one a worktree: `scripts/new-worktree.sh <type>/<task>` creates a worktree `../gotion-<task>` on that branch, the existing one (local or on origin) if there is one, otherwise a new one from `origin/main`, and runs `npm install`; it prints which case it found. Clean up with `scripts/remove-worktree.sh <type>/<task>`: it removes the worktree and deletes the branch locally and on origin, asking first if the branch has commits not in `origin/main`. A plain branch in the main checkout works as well.
- Link in the PR description the Notion tasks the PR works on: `.github/workflows/notion.yml` (logic in `.github/scripts/notion.mjs`) keeps a page per PR in the Pull Requests database on Notion, related to those tasks through their `PRs` property, and moves a task to Done when one of its PRs reaches `main` and none of the others is still open.
- After opening a PR or pushing to it, rewrite the body of its page in the Pull Requests database with the `pr-page` skill (`.claude/skills/pr-page/`): an Italian summary passed through the `humanizer` skill, the files touched with their lines, and each commit in plain words with its files and lines. The workflow owns the properties of the page, the skill its body.
- Merge only with `scripts/ff-merge.sh <PR>`: it rebases the branch on `main` (after a rebase it force-pushes and stops, because CI and a new approval are needed), then checks CI and the approval and pushes the branch head straight onto `main` as a fast-forward, then retargets onto `main` the open PRs whose base was the merged branch. It doesn't delete the branch. Never the "Rebase and merge" or "Create a merge commit" buttons: the first drops the signatures, the second breaks the linear history.
- The ruleset of `main` also requires the `success` check of the CI (the job that collects all the others, emitted by GitHub Actions) on a branch up to date with `main`, so a red CI blocks every way in, the script, a manual push or a button. Renaming the `success` job breaks the rule: update the ruleset in the same change.
- Renovate PRs (`renovate.json`) need an approval like any other; then Renovate squashes them itself once `success` is green (the script refuses bot PRs). Squash by hand only for exceptions.

## Architectural constraints (SAP)

- Distributed system, **microservices** architectural style.
- Each service internally follows **Clean** or **Hexagonal Architecture** (domain isolated from frameworks/IO).
- **DDD** end-to-end: domain model and bounded contexts identified before/alongside design (`docs/design.md`).
- Components-and-Connectors diagrams go in `docs/_includes/architecture.md`, **ADRs** in `docs/_includes/adr.md`, both included from `docs/design.md`.
- Prototype: business logic and architectural infrastructure matter, polished UI does not.

## Process constraints (SPE)

- Demonstrable DevOps process: CI **and** CD, not just tests on push (`docs/devops.md`).
- Automated deployment via containerization and/or orchestration.
- **At least two target platforms with different runtimes** — already decided in the exam proposals approved by both courses: the core backend services in **Go**, the real-time service in **Node.js/TypeScript** (WebSocket), the client in React. The same proposals fix Apache Kafka as the broker, Docker + Kubernetes (Minikube/Kind) for the deployment, Database-per-Service and Event Sourcing. Don't reopen these choices: an ADR on them records the decision, it doesn't weigh alternatives.
- SPE grading weighs domain modeling and DevOps practice heavily, independent of SAP's architecture grading — don't let one slide to satisfy the other.

## Working here

- Trace every service and architectural decision back to a user story (`docs/_includes/functional-requirements.md`) or QA scenario (`docs/_includes/quality-attributes.md`); SPE/SAP evaluation both expect that traceability.
- When proposing a new service or bounded context, check it against QA-09 (modifiability): a change should stay confined to the definition and rendering of the block type inside its owning service, with no shared-schema migration.
- If several Claude Code sessions run in parallel, give each one its own worktree and work only inside it; don't use `git stash` (it is shared by all worktrees), and leave `.git/config`, `.git/info/exclude` and the hooks alone.
- Use the skills of Superpowers only when the task has logic to test: a domain rule, an application service, an adapter, the CRDT, a script with branches. Then follow `test-driven-development`, plus `systematic-debugging` for a bug and `verification-before-completion` before calling the work done; `subagent-driven-development` and `requesting-code-review` fit a task with several pieces of such logic. For the report, the diagrams, configuration, CI, dependencies and code with no logic (the skeleton, the wiring in `main.go`), skip Superpowers: this rule is the explicit instruction its `using-superpowers` skill asks for. Use `brainstorming` and `writing-plans` only when the user asks, since the Notion task and the report already say what to build, and never `using-git-worktrees` or `finishing-a-development-branch`: worktrees, branches and merges follow the Git workflow above.
